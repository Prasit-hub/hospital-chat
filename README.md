# รวมแชท (โรงพยาบาล) — ศูนย์ประสานงานคนไข้

ระบบแชทรวมสำหรับตอบคนไข้จาก **LINE OA, Facebook Messenger, Instagram และอีเมล** (TikTok รอสิทธิ์ API) ในหน้าเดียว
แยกมาจากเวอร์ชันร้านค้า (โฟลเดอร์ `oho-clone`) — ใช้ฐานข้อมูล `hospchat` และพอร์ต Docker ทดสอบ 8180/8543 จึงรันคู่กันได้

## สิ่งที่ต่างจากเวอร์ชันร้านค้า

| เรื่อง | การทำงาน |
|---|---|
| **แฟ้มคนไข้ (Patient)** | คนไข้ 1 คน = 1 แฟ้ม มีได้หลายบัญชีช่องทาง (Contact) — หน้าแชทแสดงข้อความทุกช่องทางเป็นเส้นเวลาเดียว และเลือกได้ว่าจะตอบทางไหน |
| **รวมแฟ้ม (merge)** | ระบบแนะนำคู่ที่ HN / เบอร์โทร / อีเมล / ชื่อ ตรงกัน → เจ้าหน้าที่เทียบข้อมูลทีละช่อง เลือกค่าที่ถูก และติ๊กยืนยัน → รวม · HN ไม่ตรงกัน = รวมไม่ได้ · “ไม่ใช่คนเดียวกัน” = ไม่แนะนำคู่นั้นอีก |
| **ยกเลิก / แยก** | ผู้ดูแลยกเลิกการรวมได้ (คืนบัญชี นัด แท็ก และข้อมูลแฟ้มหลักก่อนรวม) · แยกบัญชีช่องทางเดียวออกเป็นแฟ้มใหม่ได้ |
| **งาน (Case)** | 1 งาน = 1 เรื่องที่คนไข้ติดต่อ · คนไข้มีงานเปิดได้ครั้งละ 1 งาน · สถานะ: รอรับ → กำลังทำ ⇄ รอคนไข้ตอบ → (รอแผนกรับ) → ปิด · ตอบครั้งแรก = รับงานอัตโนมัติ · คนไข้ทักหลังปิด = งานใหม่ · เปิดงานเดิมอีกครั้งได้ภายใน 7 วัน · รอคนไข้เกิน 3 วัน = ปิดอัตโนมัติ (ตั้งค่าได้) |
| **ปิดงาน** | ต้องเลือกผลการปิด + หมวดเรื่อง · ผล “แนะนำมาโรงพยาบาล / ส่งต่อภายนอก / อื่นๆ” และงานเร่งด่วนต้องมีบันทึกสรุป · “นัดหมายแล้ว” ต้องมีคำขอนัดในงาน · ส่งข้อความปิดท้ายได้ |
| **โอนงานไปแผนก** | ต้องระบุเหตุผล (และสิ่งที่ทำไปแล้ว) → เข้าคิวแผนกปลายทาง ผู้โอนยังรับผิดชอบจนกว่าจะมีคนในแผนกกดรับ · แผนกตีกลับได้ (ระบุเหตุผล) · ผู้โอนดึงกลับได้ · เตือนเมื่อไม่มีคนรับเกินเวลา (ปกติ 15 นาที / เร่งด่วนทันที ตั้งรายแผนกได้) · กดรับพร้อมกัน = ได้คนเดียว |
| **ประวัติการติดต่อ** | แฟ้มคนไข้แสดงงานทั้งหมด (รวมจากแฟ้มที่รวมมา) พร้อมผลการปิด เส้นทางการโอน ช่องทาง · คลิกเพื่อเลื่อนไปที่งานนั้นในเส้นเวลา (มีเส้นคั่นแต่ละงาน) |
| **แท็กคนไข้** | 4 หมวด: ความต้องการพิเศษ / ลักษณะการสื่อสาร / สิ่งที่ชอบ / สิ่งที่ไม่ชอบ · เลือกจากรายการกลางหรือพิมพ์ใหม่ (ใช้ได้ทันที รอผู้ดูแลรับเข้ารายการ) · แถบ “ควรรู้” บนหน้าแชท · แท็ก “ไม่ต้องการรับข่าวสาร” ตัดออกจากประกาศอัตโนมัติ |
| **ยืนยันตัวตน** | ต่องาน บันทึกวิธี เวลา ผู้ยืนยัน · งานใหม่ต้องยืนยันใหม่ · ช่องพิมพ์เตือนเมื่อยังไม่ยืนยัน |
| **เรื่องเร่งด่วน** | ตรวจคำที่ตั้งไว้ → ติดป้าย ขึ้นบนสุด ส่งข้อความแนะนำ 1669 · เจ้าหน้าที่ติด/ยกเลิกป้ายเองได้ · **รายการคำต้องให้ทีมคลินิกกำหนด** |
| **หมวดเรื่อง** | นัดหมาย, สิทธิ/ประกัน, ค่าใช้จ่าย, ผลตรวจ/เอกสาร, สอบถามอาการ, อื่นๆ |
| **คำขอนัดหมาย** | แทนออเดอร์: แผนก แพทย์ วันที่ ช่วงเวลา เหตุผล → ส่งข้อความรับเรื่อง · สถานะ รอยืนยัน → ยืนยันแล้ว (หลังลงนัดใน HIS) → มาตามนัด / ยกเลิก |
| **เห็นแชทตามแผนก** | ตั้งค่า → แผนก: “ทุกคนเห็นทุกแชท” หรือ “เห็นเฉพาะงานของแผนกตัวเอง” (ค่าเริ่มต้นของข้อมูลตัวอย่าง) — เจ้าหน้าที่เห็นงานที่ตัวเองรับผิดชอบ งานของแผนก และงานที่โอนมารอแผนกรับ · เจ้าหน้าที่ที่ไม่มีแผนกเห็นคิวกลาง · ผู้ดูแลและแผนกที่ติ๊ก “เห็นทุกแผนก” (เช่น ศูนย์ประสานงาน) เห็นทั้งหมด · มีผลกับรายการงาน แชท แฟ้ม การค้นหา แฟ้มที่อาจซ้ำ และ HIS · ในประวัติการติดต่อ งานของแผนกอื่นแสดงแค่ภาพรวม (เลขงาน วันที่ แผนก ผล) ไม่เห็นข้อความ |
| **บันทึกการใช้งาน** | รวม/ยกเลิก/แยกแฟ้ม, ยืนยันตัวตน, แก้ HN, โอน/ปิด/เปิดงานใหม่, ป้ายเร่งด่วน, แท็กคนไข้, เปิดดูประวัติ, นัดหมาย, การค้น/ดูข้อมูล HIS, เปลี่ยนการเห็นแชท — เก็บแค่ใคร/ทำอะไร/เมื่อไร ไม่เก็บเนื้อหาแชท (ตั้งค่า → บันทึกการใช้งาน) |

**เชื่อม HIS ได้ 3 แบบ** (ตั้งค่า → เชื่อมต่อ HIS): กรอก HN เอง (ค่าเริ่มต้น) · ข้อมูลจำลอง (ทดลอง/อบรม) · เชื่อม HIS Gateway จริง — ดูหัวข้อ “เชื่อมต่อ HIS” ด้านล่าง

**ก่อนใช้งานจริง ต้องให้ฝ่ายที่เกี่ยวข้องของโรงพยาบาลทบทวน:** รายการคำเร่งด่วนและข้อความตอบกลับ (ทีมคลินิก), วิธียืนยันตัวตน (`VERIFY_METHODS` ใน `src/lib/utils.ts`), การเก็บข้อมูลส่วนบุคคล/ระยะเวลาเก็บ (DPO / PDPA), ค่าการเชื่อม AD และตารางจับคู่กลุ่ม (ฝ่าย IT) ขอบเขตการเห็นแชทตามแผนก (แผนกไหนควร “เห็นทุกแผนก”) และผลการปิดงาน/เวลาเตือนการโอน (ค่าตั้งต้นเป็นข้อเสนอ ให้หน่วยงานกำหนด)

## 1. ติดตั้งและรันในเครื่อง

ต้องมี Node.js 20+ และ PostgreSQL (หรือ Docker)

**แบบสั่งเดียวจบ** (สร้าง `.env` ให้เอง → เปิด PostgreSQL → ใส่ข้อมูลตัวอย่าง → เปิด HIS จำลอง → `npm run dev`)

```bash
./scripts/dev-up.sh              # หรือดับเบิลคลิก dev-up.command บน macOS
./scripts/dev-up.sh --tunnel     # เปิด ngrok ให้ด้วย และตั้ง PUBLIC_BASE_URL อัตโนมัติ (สำหรับ webhook LINE/Meta)
./scripts/dev-up.sh --no-his     # ไม่ต้องเปิด HIS จำลอง
./scripts/dev-up.sh down         # ปิดฐานข้อมูลและตัวจำลองที่ค้างอยู่
```

กด `Ctrl+C` เพื่อหยุดแอป ตัวจำลองจะถูกปิดให้อัตโนมัติ ส่วน PostgreSQL ยังทำงานต่อ (ปิดด้วย `down`)

**แบบทีละขั้น**

```bash
npm install
cp .env.example .env          # แล้วแก้ค่าตามหัวข้อที่ 2
docker compose up -d          # เปิด PostgreSQL (ถ้ามีฐานข้อมูลอยู่แล้วข้ามได้)
npm run setup                 # prisma generate + สร้างตารางจาก prisma/migrations + ใส่ข้อมูลตัวอย่าง
npm run dev                   # เปิด http://localhost:3000
```

ตอนรัน seed ระบบจะแสดง **อีเมลและรหัสผ่าน** ของบัญชีตัวอย่าง (เจ้าของคือ `owner@example.com`) — ใช้เข้าสู่ระบบที่ `/login` แล้วเปลี่ยนรหัสผ่านทันทีจากเมนูรูปโปรไฟล์

ข้อมูลตัวอย่างใช้ช่องทาง demo ที่มี token ปลอม — ถ้าตั้ง `OUTBOUND_MODE="mock"` จะตอบแชทตัวอย่างได้โดยไม่ส่งออกไปจริง

## 2. ค่าใน `.env`

| ตัวแปร | คำอธิบาย |
|---|---|
| `DATABASE_URL` | PostgreSQL connection string |
| `ENCRYPTION_KEY` | คีย์เข้ารหัส token ของช่องทาง สร้างด้วย `openssl rand -base64 32` (**ห้ามเปลี่ยน**หลังเชื่อมช่องทางแล้ว) |
| `SEED_OWNER_PASSWORD` | รหัสผ่านเริ่มต้นของเจ้าของตอนรัน seed (เว้นว่าง = สุ่ม) |
| `PUBLIC_BASE_URL` | URL https สาธารณะของระบบ ใช้แสดง Webhook URL |
| `META_APP_SECRET` | App Secret ของ Meta App (ใช้ตรวจลายเซ็น webhook) |
| `META_VERIFY_TOKEN` | ข้อความที่ตั้งเอง ใส่ค่าเดียวกันใน Meta App Dashboard |
| `META_GRAPH_VERSION` | เวอร์ชัน Graph API (ค่าเริ่มต้น v23.0 — เช็กเวอร์ชันล่าสุดใน Meta Docs) |
| `OUTBOUND_MODE` | `live` = ส่งจริง, `mock` = ไม่ส่งออก (ทดลอง) |

## 3. เปิดให้แพลตฟอร์มเรียก webhook ได้

แพลตฟอร์มต้องเรียก URL แบบ **https** ได้ ระหว่างพัฒนาใช้ [ngrok](https://ngrok.com):

```bash
ngrok http 3000      # ได้ URL เช่น https://abcd.ngrok-free.app → ใส่ใน PUBLIC_BASE_URL
```

หรือใช้ `./scripts/dev-up.sh --tunnel` ซึ่งเปิด ngrok และเขียน `PUBLIC_BASE_URL` ใน `.env` ให้เอง (ngrok ฟรีเปลี่ยน URL ทุกครั้งที่เปิดใหม่ ต้องไปแก้ใน Console ใหม่ด้วยทุกครั้ง)

> HIS และ AD ไม่ต้องใช้อุโมงค์ เพราะรวมแชทเป็นฝ่ายเรียกออก — ใช้ตัวจำลองในเครื่อง หรือต่อ VPN เข้าวงในโรงพยาบาลได้เลย

### LINE OA
1. [LINE Developers Console](https://developers.line.biz/console/) → Provider → สร้าง **Messaging API channel**
2. คัดลอก **Channel secret** (แท็บ Basic settings) และออก **Channel access token (long-lived)** (แท็บ Messaging API)
3. ในระบบ: **ตั้งค่า → เชื่อมต่อช่องทาง → LINE → เชื่อมต่อ** วางทั้งสองค่า
4. คัดลอก Webhook URL ที่ระบบแสดง (`/api/webhooks/line/<id>`) ไปใส่ใน Console → เปิด **Use webhook** → กด Verify
5. ใน LINE Official Account Manager ปิด "Auto-reply messages" ของ LINE เพื่อไม่ให้ตอบซ้ำกับระบบ

### Facebook Messenger + Instagram
1. [Meta for Developers](https://developers.facebook.com/apps) → สร้างแอป (Business) → เพิ่ม **Messenger** และ **Instagram**
2. ตั้ง Webhook: Callback URL = `<PUBLIC_BASE_URL>/api/webhooks/meta`, Verify token = `META_VERIFY_TOKEN`
   สมัคร field: `messages`, `messaging_echoes`, `feed` (เพจ) และ `messages`, `comments` (Instagram)
3. สร้าง **Page Access Token** ของเพจ (สิทธิ์ `pages_messaging`, `pages_manage_metadata`, `instagram_manage_messages`, `instagram_manage_comments`)
4. ในระบบ: **ตั้งค่า → Messenger → เชื่อมต่อ** วาง token → ระบบจะเชื่อมเพจและ Instagram ที่ผูกอยู่ให้อัตโนมัติ
5. ก่อนเปิดให้ลูกค้าทั่วไปใช้ ต้องส่ง **App Review** และเปลี่ยนแอปเป็นโหมด Live

> ข้อจำกัด Meta: ตอบได้ภายใน 24 ชม. หลังข้อความล่าสุดของลูกค้า (ระบบเตือนและบล็อกให้) ถ้าได้สิทธิ์ Human Agent ให้ตั้ง `META_HUMAN_AGENT_TAG="true"` เพื่อขยายเป็น 7 วัน

### อีเมล
ระบบตรวจกล่องจดหมาย (INBOX) ทุก 1 นาทีผ่าน IMAP และตอบกลับผ่าน SMTP — อีเมลของลูกค้าแต่ละคนรวมเป็นแชทเดียว ตอบกลับจะอยู่ในเธรดเดิม (Re: หัวเรื่องเดิม)

1. **ตั้งค่า → เชื่อมต่อช่องทาง → อีเมล → เชื่อมต่อ**
2. **Gmail / Google Workspace**: เปิดการยืนยัน 2 ขั้นตอน แล้วสร้าง **App Password** (ค้นหา "App passwords" ในบัญชี Google) ใช้แทนรหัสผ่านปกติ — ใน Workspace ผู้ดูแลต้องเปิดให้ใช้ IMAP
3. **อีเมลโฮสติ้ง / Zoho / เซิร์ฟเวอร์บริษัท**: เลือก "อื่นๆ" แล้วใส่ IMAP/SMTP server และพอร์ตตามที่ผู้ให้บริการกำหนด (ปกติ IMAP 993 SSL, SMTP 465 SSL หรือ 587 STARTTLS)
4. ระบบทดสอบเข้าสู่ระบบทั้ง IMAP และ SMTP ก่อนบันทึก — กด "ตรวจตอนนี้" เพื่อดึงอีเมลทันที

พฤติกรรม:
- รับเฉพาะอีเมลที่เข้ามา **หลังเชื่อมต่อ** และไม่เปลี่ยนสถานะอ่าน/ไม่อ่านในกล่องจดหมาย
- ตัดข้อความเก่าที่ quote มา (On … wrote:) ออก, ข้ามอีเมลตอบกลับอัตโนมัติ/อีเมลจากตัวเอง
- รูปแนบ (≤1.5 MB, สูงสุด 4 รูป) แสดงเป็นรูปในแชท ไฟล์อื่นแสดงเป็นชื่อไฟล์แนบ
- ไม่รองรับบรอดแคสต์ทางอีเมล (เสี่ยงถูกจัดเป็นสแปม)
- **Microsoft 365 / Outlook.com**: Microsoft ปิดการเข้าสู่ระบบ IMAP/SMTP ด้วยรหัสผ่านเกือบทั้งหมดแล้ว (ต้องใช้ OAuth) จึงอาจเชื่อมต่อไม่ได้ — ปรึกษาผู้ดูแลระบบอีเมลขององค์กร
- ตั้งความถี่ตรวจอีเมลด้วย `EMAIL_POLL_SECONDS` (ค่าเริ่มต้น 60)

TikTok Business Messaging API เปิดให้เฉพาะพาร์ทเนอร์ — เมื่อได้สิทธิ์ ให้สร้าง `src/lib/channels/tiktok.ts` ตาม interface `ChannelAdapter` แล้วลงทะเบียนใน `src/lib/channels/index.ts`

### เชื่อมต่อ HIS (ตรวจคนไข้ / นัด / การมาโรงพยาบาลล่าสุด)

ตั้งค่าได้ที่ **ตั้งค่า → เชื่อมต่อ HIS** (เจ้าของเท่านั้นที่แก้ได้) เลือกได้ 3 แบบ:

| โหมด | ใช้เมื่อ |
|---|---|
| กรอก HN เอง | ยังไม่เชื่อม HIS — ทำงานเหมือนเดิม การ์ด “ข้อมูลจาก HIS” ไม่แสดง |
| ข้อมูลจำลอง | ทดลองขั้นตอนหรืออบรมเจ้าหน้าที่ ด้วยคนไข้สมมติใน `src/lib/his/mock-data.json` (ห้ามใช้ตอนเปิดบริการจริง) |
| เชื่อม HIS Gateway | ใช้ข้อมูลจริงผ่าน Gateway ของฝ่าย IT ตามสัญญา API ใน `src/lib/his/types.ts` |

ในแฟ้มคนไข้ (หน้าแชท) เจ้าหน้าที่กด **ตรวจกับ HIS** → กรอกข้อมูลที่ถามคนไข้ (HN + วันเกิด, ชื่อ + เบอร์ + วันเกิด หรือเลขบัตร + วันเกิดถ้าเปิดไว้) → เทียบข้อมูลในแชทกับ HIS → ยืนยัน → ระบบผูก HN และบันทึกการยืนยันตัวตนในงานว่า “HN + วันเกิด (ตรงกับ HIS)” จากนั้นการ์ดแสดง **นัดใน HIS** (กด “แทรกในคำตอบ” ได้) และ **การมาโรงพยาบาลล่าสุด**

กติกาที่ระบบบังคับ:
- ค้นได้เฉพาะคนไข้ที่มีงานเปิดอยู่ และต้องใช้ข้อมูลอย่างน้อย 2 อย่าง (วันเกิดเสมอ)
- ดูนัด / การมาโรงพยาบาลได้เมื่อยืนยันตัวตนในงานนั้นแล้ว · แก้ HN หรือวันเกิดเองแล้วต้องตรวจกับ HIS ใหม่
- ไม่ดึงข้อมูลทางคลินิก · ข้อมูลจาก HIS อยู่ในหน่วยความจำ 10 นาที ไม่ลงฐานข้อมูล · บันทึกการใช้งานเก็บแค่ใคร/แฟ้มไหน/ผลพบหรือไม่พบ
- จำกัด 20 ครั้ง/นาที ต่อเจ้าหน้าที่ (`HIS_RATE_PER_MIN`) · HIS ไม่ตอบ 3 วินาที (ตั้งได้) → ลองใหม่ 1 ครั้ง · พลาด 5 ครั้งใน 1 นาที → หยุดเรียก 30 วินาที แชทยังใช้ได้ตามปกติ
- คำขอนัดของรวมแชทที่ HIS ลงนัดแล้ว (HIS เก็บเลข `APT-xxxxx` ไว้ใน `sourceRef`) จะผูกเลขนัดและเปลี่ยนเป็น “ยืนยันแล้ว” อัตโนมัติ
- secret / token เข้ารหัสก่อนเก็บ · ในโหมด production ต้องใช้ `https://` (ยกเว้นตั้ง `HIS_ALLOW_HTTP=1` เมื่ออยู่ในเครือข่ายภายในที่เข้ารหัสแล้ว)
- mTLS: ให้ทำที่ reverse proxy / sidecar ระหว่างรวมแชทกับ Gateway (ตัวแอปส่ง OAuth2 หรือ Bearer token)

**ทดสอบโหมดเชื่อม Gateway ก่อนมีของจริง:** รัน `node scripts/mock-his-gateway.mjs` (พอร์ต 4700) แล้วตั้งค่า ที่อยู่ `http://localhost:4700` · OAuth2 · token `http://localhost:4700/oauth/token` · client id `chat-app` · secret `mock-secret` แล้วกด “ทดสอบการเชื่อมต่อ” — ไฟล์นี้เป็นตัวอย่างให้ฝ่าย IT ดูว่า Gateway ต้องตอบอะไร

### เข้าสู่ระบบด้วยบัญชี AD

ตั้งค่าได้ที่ **ตั้งค่า → การเข้าสู่ระบบ (AD)** (เจ้าของเท่านั้นที่แก้ได้):

| โหมด | ใช้เมื่อ |
|---|---|
| รหัสผ่านในระบบ | แบบเดิม — ค่าเริ่มต้น |
| AD จำลอง | ทดลอง/อบรมด้วยบัญชีสมมติใน `src/lib/ad/mock-directory.json` (รหัสผ่าน `Mock@1234`) เช่น `mali.s` (อายุรกรรม), `pichai.f` (การเงิน), `noi.c` (ศูนย์ประสานงาน), `it.admin` (ผู้ดูแล), `old.staff` (ถูกปิด), `guest.user` (ไม่มีสิทธิ์) |
| Active Directory | เชื่อม AD จริงผ่าน LDAPS (หรือ LDAP + StartTLS) ด้วยบัญชีบริการแบบอ่านอย่างเดียว |

- เจ้าหน้าที่พิมพ์ชื่อผู้ใช้ AD ได้ทั้ง `mali.s`, `HOSPITAL\mali.s` หรือ `mali.s@hospital.local`
- **ตารางจับคู่กลุ่ม**: กลุ่มใน AD → สิทธิ์ (ผู้ดูแล / เจ้าหน้าที่) และแผนก · ต้องอยู่ในกลุ่มที่ให้สิทธิ์อย่างน้อย 1 กลุ่มจึงเข้าได้ · บทบาท ชื่อ และแผนกซิงก์จาก AD ทุกครั้งที่เข้าสู่ระบบ (เจ้าของคงบทบาทเดิม)
- เข้าครั้งแรก = สร้างบัญชีให้อัตโนมัติ (ปิดได้) · บัญชีเดิมที่อีเมลตรงกันจะถูกผูกเป็นบัญชี AD
- ปิดบัญชีใน AD → เข้าไม่ได้ และบัญชีในรวมแชทถูกปิด + ตัด session ทันทีที่พยายามเข้า · ปิดบัญชีในรวมแชทเองก็ยังเข้าไม่ได้แม้ AD ปกติ
- โหมด AD: เข้าด้วยรหัสผ่านในระบบได้เฉพาะ **เจ้าของ** (บัญชีฉุกเฉินเมื่อ AD ล่ม) — เลือก “ทุกบัญชีที่ไม่ใช่ AD” ได้ช่วงย้ายระบบ
- session ของบัญชี AD หมดอายุตามที่ตั้ง (ค่าเริ่มต้น 12 ชั่วโมง) · บัญชี AD เปลี่ยนรหัสผ่าน/บทบาทในรวมแชทไม่ได้
- รหัสผ่านบัญชีบริการเข้ารหัสก่อนเก็บ · กันการฉีดตัวกรอง LDAP · ไม่ยอมรับรหัสผ่านว่าง · production บังคับ ldaps:// หรือ StartTLS (ยกเว้นตั้ง `LDAP_ALLOW_PLAIN=1`)
- บันทึกการใช้งาน: เข้าสู่ระบบ / เข้าไม่สำเร็จ (พร้อมเหตุผล) / สร้างบัญชีอัตโนมัติ / แก้การตั้งค่า — ไม่บันทึกรหัสผ่าน
- ปุ่ม “ค้นใน AD” ในหน้าตั้งค่า ใช้ตรวจว่าผู้ใช้คนหนึ่งจะได้สิทธิ์/แผนกอะไร โดยไม่ต้องรู้รหัสผ่านของเขา

**สิ่งที่ต้องขอจากฝ่าย IT:** ที่อยู่ DC (ldaps://…:636), Base DN ของผู้ใช้, บัญชีบริการอ่านอย่างเดียว, ชื่อกลุ่มที่จะใช้ (เช่น `RuamChat-Users`, `RuamChat-Admins`, กลุ่มแผนก) และใบรับรอง CA ของโดเมน (ใส่ใน `NODE_EXTRA_CA_CERTS`)

## 4. ทีม สิทธิ์ และการตั้งค่า

| บทบาท | ทำอะไรได้ |
|---|---|
| เจ้าของ | ทุกอย่าง รวมถึงจัดการบัญชีเจ้าของคนอื่น |
| ผู้ดูแล | เชื่อมช่องทาง เพิ่ม/ปิดบัญชีทีม ตั้งค่าร้าน ส่งบรอดแคสต์ |
| แอดมินตอบแชท | ตอบแชท จัดการลูกค้า/ออเดอร์ ดูรายงาน |

- เพิ่มสมาชิกที่ **ตั้งค่า → ทีมและสิทธิ์** ระบบจะสร้างรหัสผ่านชั่วคราวให้ส่งต่อเอง (ยังไม่มีระบบส่งอีเมล) ปุ่มรูปกุญแจใช้ออกรหัสใหม่เมื่อสมาชิกลืมรหัส
- ปิดใช้งานบัญชี = ออกจากระบบทุกอุปกรณ์ทันที และแชทที่ค้างอยู่กลับเข้าคิว "ยังไม่มอบหมาย"
- ล็อกอินผิดเกิน 10 ครั้ง/15 นาที (ต่ออีเมล+IP) จะถูกพักชั่วคราว
- ข้อความสำเร็จรูป ตอบกลับอัตโนมัติ (ต้อนรับ / นอกเวลาทำการ / คีย์เวิร์ด) แท็ก และข้อมูลการชำระเงิน แก้ได้จากหน้าตั้งค่า

### บรอดแคสต์
- เลือกช่องทาง + กลุ่มเป้าหมาย (ทั้งหมด หรือตามแท็ก) ส่งทันทีหรือตั้งเวลา
- LINE ส่งแบบ multicast (นับโควตาข้อความตามแพ็กเกจ OA)
- Messenger/Instagram ส่งได้เฉพาะลูกค้าที่ทักมาภายใน 24 ชม. — ระบบข้ามคนที่เกินและแสดงจำนวนที่ข้าม
- ตัวจับเวลาตรวจรายการที่ถึงเวลาทุก 30 วินาที (`src/instrumentation-node.ts`)

### รายงาน
คำนวณจากฐานข้อมูลจริงตามช่วง วันนี้ / 7 วัน / 30 วัน เทียบช่วงก่อนหน้า: แชทที่ลูกค้าทัก, ลูกค้าใหม่, เวลาตอบครั้งแรกเฉลี่ย, แชทที่ปิด, ยอดขาย (ออเดอร์ชำระแล้ว/ส่งแล้ว), จำนวนออเดอร์, ข้อความรายชั่วโมง, แยกช่องทาง และผลงานแอดมินแต่ละคน

## 5. การทำงานของระบบ

```
LINE / Meta ──webhook──▶ /api/webhooks/*  (ตรวจลายเซ็น → ตอบ 200 ทันที)
                               │ after()
                               ▼
                    Adapter แปลงเป็น IncomingEvent
                               ▼
              ingest(): ลูกค้า → ห้องแชท → ข้อความ (กันซ้ำด้วย externalId)
                               │           └─ ตอบอัตโนมัติ (ต้อนรับ / คีย์เวิร์ด / นอกเวลา)
                               ▼
                    publish() ──SSE──▶ หน้าจอแอดมิน (/api/events)

แอดมินตอบ ──▶ POST /api/conversations/:id/messages ──▶ Adapter.send() ──▶ LINE / Meta
```

- **LINE**: ใช้ reply token (ฟรี) ก่อนถ้ายังไม่หมดอายุ ไม่งั้นใช้ push (นับโควตาตามแพ็กเกจ OA)
- **คอมเมนต์ FB/IG**: เข้ามาเป็นแชทประเภท "คอมเมนต์" ตอบกลับเป็น private reply ไปทาง DM
- **token ทุกช่องทาง** เข้ารหัส AES-256-GCM ก่อนเก็บลงฐานข้อมูล

### โครงสร้างไฟล์หลัก

```

src/lib/inbox/service.ts       ingest ขาเข้า, sendOutgoing ขาออก, ตอบกลับอัตโนมัติ
src/lib/realtime.ts            ตัวกระจายเหตุการณ์ (SSE)
src/app/api/webhooks/          รับ webhook
src/app/api/…                  API ของหน้าจอ (inbox, conversations, patients, appointments, departments, audit, channels, team, settings, broadcasts, dashboard)
```

### แก้โครงสร้างฐานข้อมูล

## 7. Neon + Render สำหรับ dev/preview (production ยังอยู่ที่ Azure VM เท่านั้น)

**สรุปก่อน:** ใช้ชุดนี้ได้สำหรับ "ดูหน้าจอ" ระหว่างพัฒนา แชร์ลิงก์ preview ให้คนอื่นดูเร็วๆ หรือทดสอบ UI/ฟอร์ม — **ยังไม่แนะนำให้ใช้เป็นระบบจริงหรือรับ webhook จริงจากคนไข้**

Render ต่างจาก Vercel ตรงที่รัน container ยืนตลอดจริง (ไม่ใช่ serverless) จึง SSE และตัวจับเวลาเบื้องหลังทำงานได้ตามปกติ — **แต่** แผนฟรีของ Render หลับหลังไม่มีคนเข้า 15 นาที (ตื่นใช้เวลา ~1 นาทีตอนมี request ใหม่):

| ส่วน | เป็นยังไงบน Render (แผนฟรี) |
|---|---|
| Realtime (SSE, `src/app/api/events`) | ทำงานได้ปกติระหว่าง container ตื่นอยู่ (instance เดียว ไม่มีปัญหา pub/sub ข้าม instance แบบ Vercel) — แต่ถ้า container หลับ การเชื่อมต่อ SSE เดิมจะหลุด ต้องรอ "ตื่น" ใหม่ |
| ตัวจับเวลาเบื้องหลัง (`src/instrumentation-node.ts`) | ทำงานได้ตามปกติตอน container ตื่นอยู่ แต่ **หยุดทำงานตอนหลับ** — ส่งบรอดแคสต์ตามเวลา/ตรวจอีเมล/ปิดงานอัตโนมัติ จึงคลาดเคลื่อนได้ถ้าไม่มีคนเข้าระบบนานๆ ถ้าไม่ต้องการให้ทำงานเลยตอน dev ตั้ง `DISABLE_SCHEDULER=true` ได้ |
| Webhook จาก LINE/Meta ที่ต้องมาถึงแน่นอน | ถ้า webhook มาถึงตอน container หลับอยู่ คำขอแรกต้องรอ container ตื่น (~1 นาที) เสี่ยง timeout ฝั่ง LINE/Meta และข้อความอาจหาย ใช้ Azure VM (DEPLOY.md) สำหรับการเชื่อมช่องทางจริงเท่านั้น |

### 7.1 ตั้งฐานข้อมูล develop ให้เป็น Neon

[Neon](https://neon.tech) เป็น PostgreSQL บนคลาวด์ มีแผนฟรี ใช้แทน `docker compose up -d` ตอน dev ได้ ไม่ต้องรัน PostgreSQL ในเครื่อง (และ Render free Postgres หมดอายุใน 30 วัน จึงใช้ Neon เป็นฐานข้อมูลของ preview ด้วย)

1. สมัคร Neon → สร้างโปรเจกต์ → สร้างฐานข้อมูลชื่อ `hospchat`
2. หน้า Connection Details จะให้ 2 connection string มา:
   - **Pooled connection** (โฮสต์มีคำว่า `-pooler`) — ใช้เป็น `DATABASE_URL` สำหรับรันแอปตามปกติ
   - **Direct connection** (ไม่มี `-pooler`) — ใช้เป็น `DIRECT_URL` เฉพาะตอน migrate (ดูหัวข้อ 7.2)
3. ใส่ใน `.env`:
   ```
   DATABASE_URL="postgresql://<user>:<password>@<project>-pooler.<region>.aws.neon.tech/hospchat?sslmode=require"
   ```
4. รัน `npx prisma migrate deploy && npx prisma db seed` แล้ว `npm run dev` ได้ตามปกติ — โค้ดไม่ต้องแก้อะไร เพราะ `@prisma/adapter-pg` ต่อ Neon ผ่าน `DATABASE_URL` ตรงๆ (Neon คุย wire protocol ของ PostgreSQL ปกติ)

ข้อดีของการใช้ Neon ตอน dev: เปิดเครื่องใหม่ไม่ต้องรอ PostgreSQL บูต และแชร์ข้อมูลทดสอบชุดเดียวกันกับเพื่อนร่วมทีมได้ (ระวัง: อย่าใส่ข้อมูลคนไข้จริงแม้เป็นฐานทดสอบ)

### 7.2 Deploy preview ขึ้น Render

Render build จาก `Dockerfile` เดิมของโปรเจกต์ตรงๆ (stage สุดท้ายในไฟล์คือ `render` ซึ่งรัน `prisma migrate deploy` ให้อัตโนมัติก่อนเปิดเซิร์ฟเวอร์ทุกครั้งที่ container เริ่ม เพราะแผนฟรีของ Render ไม่มี pre-deploy command แยกต่างหาก)

**แบบเร็ว (Blueprint):** เชื่อม repo กับ Render แล้วเลือก **New → Blueprint** — Render จะอ่าน `render.yaml` ที่เตรียมไว้ให้ และสร้างบริการแบบ Docker บนแผนฟรีให้เองพร้อมช่องให้กรอก env ที่เป็นความลับ

**หรือสร้างเองทีละขั้น:** New → Web Service → เลือก repo นี้ → Runtime: **Docker** → Dockerfile Path: `./Dockerfile` (ไม่ต้องระบุ target ใน Advanced — Render ใช้ stage สุดท้ายของไฟล์เป็นค่าเริ่มต้นอยู่แล้ว) → Plan: **Free**

ตั้งค่า Environment Variables (ทำได้ทั้งสองแบบด้านบน):

| ตัวแปร | ค่า |
|---|---|
| `DATABASE_URL` | connection string **แบบ pooled** จาก Neon |
| `DIRECT_URL` | connection string **แบบ direct** จาก Neon (ให้ `prisma migrate deploy` ใช้ตอน container เริ่ม) |
| `ENCRYPTION_KEY` | สร้างใหม่ด้วย `openssl rand -base64 32` (คนละตัวกับ production) — ถ้าใช้ Blueprint ตัวนี้สุ่มให้อัตโนมัติ |
| `SEED_OWNER_PASSWORD` | ตั้งรหัสผ่านทดสอบของตัวเอง |
| `OUTBOUND_MODE` | `"mock"` เสมอ — กันข้อความหลุดไปหาคนไข้จริง |
| `DISABLE_SCHEDULER` | `"true"` แนะนำไว้ตอน dev (ดูเหตุผลด้านบน) |
| `PUBLIC_BASE_URL` | URL ที่ Render ให้มา เช่น `https://ruamchat-preview.onrender.com` (รู้ URL หลัง deploy ครั้งแรกแล้วค่อยกลับมาใส่) |
| `NEXT_PUBLIC_APP_TZ` | `"Asia/Bangkok"` |

Deploy แล้วเข้า `/login` ด้วยบัญชีจาก `SEED_OWNER_PASSWORD` ที่ตั้งไว้ ใช้ดูหน้าจอ ทดสอบฟอร์ม และทดสอบ HIS/AD แบบ **ข้อมูลจำลอง** ได้ตามปกติ (ไม่ต้องมีอุโมงค์ใดๆ เพราะ HIS/AD จำลองอยู่ในตัวแอปเอง) ครั้งแรกที่เปิดหลัง container หลับ หน้าจอจะโหลดช้าประมาณ 1 นาที เป็นเรื่องปกติของแผนฟรี

**อย่าผูก LINE OA หรือ Meta App จริงเข้ากับ URL ของ Render preview** แม้จะตั้ง `OUTBOUND_MODE=mock` ไว้ เพราะช่วงที่ container หลับ webhook อาจมาไม่ถึงหรือข้อความเข้าไม่ครบตามเหตุผลในตารางด้านบน

### 7.3 Production ยังคงเป็น Azure VM เท่านั้น

ค่าตั้งต้นสำหรับขึ้นระบบจริงไม่เปลี่ยนจาก **[DEPLOY.md](DEPLOY.md)** — เซิร์ฟเวอร์ Ubuntu เดียวรัน PostgreSQL ในเครื่อง (ไม่ใช่ Neon), ไม่หลับ, ตัวจับเวลาเบื้องหลังทำงานได้เต็มที่ตลอดเวลา และ SSE เชื่อมต่อได้ต่อเนื่องเพราะมี process เดียวที่รันค้างตลอด — ตรงกับสิ่งที่ระบบนี้ต้องการจริงๆ

ใช้ Neon + Render สำหรับ **dev และ preview เท่านั้น**
